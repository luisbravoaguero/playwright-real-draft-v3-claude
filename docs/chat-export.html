Analysis report: OIM test automation framework (Playwright + Java)

The project is a separate, black-box UI test framework for MAPFRE Perú's OIM portal (oim.pre.mapfre.com.pe). It contains no application code. It has about 300 source files: 25k lines of page objects and 5k lines of step definitions. I checked that it compiles: mvn -o test-compile passes with Java 17.

Business areas covered: policy quote and issuance for Auto (new and used, with inspection), SOAT, SCTR (short and regular period), Vida Ley, Accidentes, Salud, Vida Individual, Vida Inversión, FOLA, Decesos, Camposanto, Transporte and Riesgos Generales; the Constancias SCTR / SCTR Minería / Vida Ley module (declaración, inclusión, manual, reemplazo, reimpresión, anulación, mes vencido); and Inspección de Autos.

How one scenario runs

  1. The TestNG data provider hands scenarios to threads (dp.threads, default 1; Jenkins uses 2).
  2. Hooks.@Before sets up the screenshot sink, then DriverFactory.init() creates a full Playwright instance, browser, context and page for that scenario, stored per thread, and creates the Extent test.
  3. Step classes get a PageProvider and a ScenarioContext through PicoContainer and build their page objects in the constructor.
  4. Page methods follow an action + UiSync.waitForAppIdle pattern (spinner hidden and stays hidden for 250 ms). Harder transitions use race utilities such as FirstAppearanceRace (error vs success vs timeout).
  5. @After takes a screenshot on failure, then DriverManager.cleanup() and clears per-thread state.

CI pipeline (JenkinsCI)

  1. Discover: Cucumber dry run with the chosen tags → JSON → list of feature:line entries.
  2. Split: list cut into groups of 2, each group gets its own Kubernetes pod, all in parallel; each pod runs 2 threads.
  3. Per pod: runs tests, strips - #1 suffixes from JUnit names (for Octane), publishes JUnit, stashes extent.json.
  4. Merge: ExtentJsonMergeMain via exec:java merges all pods' JSON into one Spark HTML report, published with publishHTML and archived.

3. Strengths

  • Clean layering; ArtifactSink stops src/main from depending on Cucumber.
  • Built for parallel runs: per-thread driver and Extent state, PicoContainer-scoped scenario state.
  • Modern locators: ~580 getByRole, 195 getByText, 83 getByLabel vs 27 XPath.
  • App-aware synchronization (spinner waves + quiet period, first-appearance races).
  • 12-factor configuration: any key can be overridden with -D or an environment variable.
  • Rich evidence: screenshots per step node, named checkpoints, readable console log with timings.
  • Living docs in docsFeatures/*.md.

4. Findings and risks

🔴 High

  1. Plain-text credentials and an internal URL in the repo (user.email=WEBMASTER, user.password=… in global.properties). LoginPage read them via ConfigManager.getProperty, which skips the -D/ENV override. Rotate the password.
  2. RandomData returns the same values every time. rnd() builds new Random(SeedManager.seed()) on every call with the same per-thread seed, and SeedManager.clear() is never called — plate/VIN/engine repeat across scenarios on the same thread.
  3. The runner hardcodes tags = "@riesgosgenerales".

🟠 Medium

  1. Two screenshots per step (@AfterStep + ExtentCucumberStepsPlugin).
  2. A full Playwright instance and browser start per scenario (~1–2 s each).
  3. DriverManager.cleanup() is not exception-safe.
  4. ElementAsserts discards the original error (no cause).
  5. Fixed waits: 54 waitForTimeout, 2 Thread.sleep, waitRandomBetween, JS clicks in clickMenuOption.
  6. JavaScript built by string concatenation in clickMenuOption.
  7. 143 broad catch (Exception …) and 73 System.out.println.

🟡 Low / maintainability

  1. Very long steps (up to 16 parameters); all 81 scenarios are single-row Scenario Outlines; no Background.
  2. BasePage is an 889-line catch-all with near-duplicate helpers and mixed-language names.
  3. Inconsistent tags (@regresion/@Regresion) and typos in folder/step names; leftover files.
  4. Placeholder Maven metadata (org.example), no Maven Wrapper, saucedemo URLs, unused implicitWait.
  5. Hardcoded relative paths in TemplateFactory.
  6. Reporting split across src/main and src/test; double flush.
  7. No unit tests for utilities, no static analysis, no README.

5. Recommended next steps

  1. Remove the credentials, rotate the password, switch LoginPage to getGlobal.
  2. Fix RandomData/SeedManager.
  3. Remove the hardcoded runner tag.
  4. One screenshot per step; safer cleanup() and ElementAsserts.
  5. One browser per thread, one context per scenario; state-based waits.
  6. Gradual refactor: Background for login, shorter steps, split BasePage, one tag convention.

Create the file at the project root, next to pom.xml, not under src/:

D:\workspace\playwright-real-draft-v3-claude\
├─ pom.xml
├─ JenkinsCI
├─ config\
│  └─ local\
│     └─ global.properties   ← create this
└─ src\...

Contents: only the keys you want to override.

user.email=WEBMASTER
user.password=YourNewPasswordHere

To create it from PowerShell in the project root:

New-Item -ItemType Directory -Force config\local
@'
user.email=WEBMASTER
user.password=YourNewPasswordHere
'@ | Out-File -Encoding utf8 config\local\global.properties
  • Working directory: the path is resolved from where tests run. mvn test from the project root works; in IntelliJ the run configuration's working directory must be the project root.
  • Format: Java .properties, read as UTF-8. Write a backslash as \\; trailing spaces are kept.
  • Priority: -Duser.password=... or USER_PASSWORD replaces the file value.
  • Git: config/local/ is in .gitignore.
  • Other settings: the file can override any other global.properties key for your machine only.
  • Password: use the rotated password.

1. Where Jenkins gets the user and password

Jenkins never sees config/local/global.properties; that file lives only on your laptop. Jenkins uses environment variables, which ConfigManager checks before any file:

Key the code asks forEnvironment variable it checks
user.emailUSER_EMAIL
user.passwordUSER_PASSWORD

Step 1: create the credential in Jenkins (Manage Jenkins → Credentials → Add Credentials): Kind = Username with password; Username = WEBMASTER; Password = the new password; ID = oim-qa-login.

Step 2: wrap the mvn test in the pod stage with withCredentials:

catchError(buildResult: 'UNSTABLE', stageResult: 'UNSTABLE') {
  withCredentials([usernamePassword(credentialsId: 'oim-qa-login',
                                    usernameVariable: 'USER_EMAIL',
                                    passwordVariable: 'USER_PASSWORD')]) {
    sh """
      mvn -B -q test \
        ...   (same flags as today)
    """
  }
}

Jenkins sets the two variables and masks the password in the log. The Discover and Merge stages don't log in and don't need it.

  • Your laptop: config/local/global.properties (or environment variables).
  • Jenkins: Jenkins credential store → USER_EMAIL / USER_PASSWORD.
  • The repo: nowhere.

2. src/main/resources/global.properties is still needed

It is the main settings file everyone uses, including Jenkins. The local file only overrides the keys written in it. Example with a local file containing only the two credentials:

3. When to write \\

Only if your password contains a backslash. For a real password Mapfre\2025:

What you write in the fileWhat the code receivesCorrect?
user.password=Mapfre\2025Mapfre2025❌ login fails
user.password=Mapfre\\2025Mapfre\2025✅
  • A leading space: user.password=\ abc gives abc.
  • A trailing backslash (abc\): write abc\\.
  • . ! @ # $ % = : in the middle need no escaping.
  • Environment variables in Jenkins take the value exactly as typed.
